# Story 2.7 — Conformidade com o padrão de segurança da MaisTODOS

- **Épico:** E2 · **Sprint:** 3 · **Bloqueio:** 🟢 · **Status:** Concluída

## Contexto

O Matheus disponibilizou o `SECURITY.md` do **Hub MaisTODOS** — o padrão que a TI já aceita,
mencionado na reunião de 28/08 ("tenho um arquivo que é a organização de segurança que a
MaisTODOS aceita pela parte da TI"). Esta story alinha o Painel de Crédito PJ a ele.

O arquivo de referência foi movido para `docs/referencias/SECURITY-hub-maistodos.md`, e este
projeto ganhou o seu próprio `SECURITY.md` no mesmo formato.

## O que o padrão exigia e não estava atendido

| Item do padrão | Situação anterior | Ação |
|---|---|---|
| `search_path = public, pg_catalog` fixo em funções | Usávamos só `public` | Alinhado nas 7 funções novas |
| `verify_jwt = true` explícito nas Edge Functions | `config.toml` só tinha `project_id` | Declarado para as 8 functions |
| Sanitização server-side de conteúdo | E-mail montado no cliente com HTML livre | **Vetor eliminado** — ver abaixo |
| Cabeçalhos HTTP com meta nota A/A+ | Já feito no nginx | Documentada a alternativa via Traefik |
| Auditoria de `dangerouslySetInnerHTML` | Não auditado | Auditado — só `chart.tsx` (CSS do shadcn, sem input de usuário) |

## A mudança mais relevante: o e-mail

O padrão do Hub trata XSS com sanitização em duas camadas (DOMPurify no front + CHECK
constraints no banco). Aqui o problema era outro e maior: **o cliente montava o HTML do
e-mail e escolhia os destinatários**.

Mesmo depois de a Story 2.5 exigir JWT, isso continuava sendo um vetor: bastava uma conta
comprometida — inclusive do time externo do fundo — para enviar qualquer conteúdo, para
qualquer endereço, com a marca da MaisTODOS.

**Solução: eliminar o vetor por construção em vez de sanitizar.**

| Antes | Depois |
|---|---|
| Cliente envia `{ to, subject, html }` | Cliente envia `{ operacao_id, evento, detalhe? }` |
| HTML arbitrário | HTML montado no servidor, todo dado escapado |
| Destinatários informados pelo cliente | Destinatários lidos do campo `destinatarios` da operação |
| Qualquer operação | Operação lida com o client do usuário — **passa pela RLS** |

Quem não enxerga a operação não consegue disparar e-mail sobre ela. E o e-mail de teste vai
sempre para o próprio usuário autenticado, resolvido no servidor.

## Correção adicional descoberta no caminho

A página do funil chamava `salvarOperacao` sem aguardar e disparava a notificação em seguida.
Como a edge function agora lê a operação **do banco**, isso viraria corrida: o e-mail sairia
com a etapa anterior.

Criado `salvarENotificar`, que aguarda a gravação e só então notifica — e não notifica se a
gravação falhar. Além de corrigir a corrida, elimina o caso de "e-mail avisando de uma
mudança que não chegou a ser gravada", que era pior do que nenhum e-mail. Falha de gravação
agora vira aviso visível na tela, em vez de erro silencioso no console.

## Onde ficamos mais rígidos que o Hub

| Item | Hub | Aqui | Por quê |
|---|---|---|---|
| Auth hardening | Postergado até o SSO | **Feito já** | O Hub só tem 12 internos; aqui há usuário externo com dado financeiro |
| CSP `script-src` | `'self' 'unsafe-inline'` | `'self'` | O bundle do Vite não precisa de inline |
| `xlsx` | Risco aceito | **Resolvido** | Migrado para a distribuição oficial da SheetJS |
| Cabeçalhos HTTP | Pendente com o time de infra | Aplicados no nginx da imagem | Não dependemos de terceiros |

> **Sugestão para o Hub:** a troca do `xlsx` pela distribuição da SheetJS resolve o item
> equivalente no `SECURITY.md` de lá sem esperar a refatoração para `exceljs`. API compatível
> — aqui nenhum código precisou mudar.
