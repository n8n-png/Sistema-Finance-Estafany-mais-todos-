## Decisões

**Funções puras continuam puras.** `moverEtapa` e `registrarMovimentacao` retornam um novo
objeto e são chamadas de forma síncrona por `OperacoesValora.tsx`. Torná-las `async` obrigaria
a reescrever a página. A gravação ficou concentrada em `salvarOperacao`, que já era `async` e
já era chamada no ponto certo (`atualizar`).

**Divisão do histórico.** A mudança de etapa é registrada pelo **trigger** no banco; a aplicação
grava apenas as notas descritivas ("Operação aprovada — aguardando emissão de contrato").
O trigger registra o *fato* auditável, a aplicação registra o *porquê*. Por isso a policy de
INSERT do histórico exige `etapa_de`/`etapa_para` nulos: a aplicação não pode forjar uma
mudança de etapa na trilha de auditoria.

**Cinco consultas em paralelo, não joins aninhados.** A RLS das tabelas filhas já filtra pela
permissão da operação-pai, então o resultado é idêntico e cada consulta continua simples de
auditar.

## Armadilha encontrada (vale registrar)

Os tipos de linha em `funil.ts` **precisam ser `type`, nunca `interface`**.

O supabase-js exige que o schema satisfaça `GenericSchema`, cujo `Row` é `Record<string, unknown>`.
O TypeScript não considera `interface` atribuível a `Record<string, unknown>` — só type aliases,
que ganham index signature implícito. Com `interface`, o genérico `Schema` do `SupabaseClient`
colapsa para `never`, e o sintoma é traiçoeiro: **o `select` continua compilando normalmente**
(mascarando o problema) enquanto todo `insert`/`update` falha com
`not assignable to parameter of type 'never'`.

O aviso está no cabeçalho do arquivo para não repetirmos isso quando o schema crescer.
