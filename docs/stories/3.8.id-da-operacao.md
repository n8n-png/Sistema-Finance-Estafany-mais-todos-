# Story 3.8 — Geração automática do ID da Operação

- **Épico:** E3 · **Bloqueio:** 🟡 escolha do formato · **Status:** Especificada
- **Origem:** resposta da Lavínia em 04/09/2026

## História

**Como** Lavínia,
**quero** que o painel gere o ID da operação automaticamente ao desembolsar,
**para que** eu pare de montar esse código à mão numa planilha e o HubSpot receba o valor sozinho.

## Situação atual

> *"Esse ID é calculado manualmente quando uma operação está sendo enviada para a coluna
> 'desembolsado'. Ela é feita através de uma fórmula (concatenar) no Excel."*

Hoje: a operação chega ao desembolso → a Lavínia abre a planilha → copia os dados → a fórmula
gera o código → ela cola no HubSpot. Trabalho manual e sujeito a erro de digitação.

## A fórmula, decifrada e validada

```
=CONCATENAR(
  SE(E2="PÓS";"POS";SE(E2="PRÉ";"PF";SE(E2="PRÉ/PÓS";"POS";SE(E2="FUMAÇA";"FUM";"SEM TIPO DE OP."))));
  C2;                  → data de desembolso
  ESQUERDA(A2;3);      → 3 primeiras letras da unidade
  ESQUERDA(B2;2)       → 2 primeiros dígitos do CNPJ
)
```

### ⚠️ O achado: o número do meio é o serial de data do Excel

O trecho `C2` não gera uma data legível — gera o **número serial** que o Excel usa
internamente para datas (dias desde 30/12/1899).

`46262` **é** 28/08/2026. Mas ninguém olha para `46262` e enxerga uma data.

Isso é um artefato da ferramenta que vazou para dentro do identificador de negócio. Ao sair
da planilha, deixa de fazer sentido — nenhum sistema fora do Excel usa essa contagem.

| GUARATINGUETA | 22941234000176 | 29/07/2026 | PRÉ/PÓS | `POS46232GUA22` | `POS46232GUA22` | ✅ |

**5 de 5.** A regra está fechada e reproduzível.

### Mapa das siglas

| Tipo de operação | Sigla |
|---|---|
| PÓS | `POS` |
| PRÉ | `PF` |
| PRÉ/PÓS | `POS` |
| FUMAÇA | `FUM` |
| qualquer outro | `SEM TIPO DE OP.` |

Observação: `PRÉ` vira `PF` (2 letras) enquanto os outros usam 3 — por isso o ID tem 12 ou 13
caracteres, não um tamanho fixo.

## 🔴 A inconsistência: existem dois formatos na mesma planilha

A captura enviada mostra, numa área destacada em amarelo, a especificação de um formato
**diferente** do que a fórmula produz:

| Componente (legenda amarela) | Tamanho |
|---|---|
| taxa (pos/pre) | 3 |
| sigla da unidade (cdt / vdt / as / all) | 3 |
| data sem barras | 6 |
| 3 primeiros dígitos do CNPJ | 3 |
| 3 últimos dígitos do CNPJ | 3 |
| número de parcelas | 2 |
| **total** | **20** |

Comparando com o que a fórmula realmente gera hoje:

| Item | Fórmula atual | Legenda amarela |
|---|---|---|
| Tamanho | 12–13 caracteres | 20 caracteres |
| Identificação da unidade | 3 letras do **nome** (`IBI`, `CRI`) | sigla da **linha de crédito** (`cdt`, `vdt`, `as`) |
| Data | serial do Excel (`46262`) | data sem barras, 6 dígitos |
| CNPJ | 2 primeiros dígitos | 3 primeiros **e** 3 últimos |
| Parcelas | não entra | 2 dígitos |

A leitura mais provável: **a legenda amarela é o formato desejado, ainda não implementado**, e
a fórmula é o que roda hoje.

**Precisa de decisão antes de codificar.** As duas opções são defensáveis:

| Opção | A favor | Contra |
|---|---|---|
| **Replicar a fórmula atual** | Continuidade total com os IDs já existentes no HubSpot e na planilha | Perpetua o serial do Excel, que é ilegível fora dela |
| **Adotar o formato de 20 caracteres** | Legível, mais informação, identifica a linha de crédito | Cria dois padrões: histórico num formato, novos em outro |

**Recomendação:** adotar o formato novo, **se** a área confirmar que era esse o plano.
O momento de trocar é agora — quando a geração sai da planilha e passa a ser automática.
Depois de gerar centenas de IDs no formato antigo, a migração fica bem mais cara.

Se escolherem o formato novo, faltam definir:
- as siglas por linha (`cdt` = QIA/Cartão de TODOS? `as` = Amor Saúde? `vdt` = Visão de TODOS? o que é `all`?)
- a ordem exata dos componentes
- o formato da data de 6 dígitos: `DDMMAA` ou `AAMMDD`?

## Critérios de aceitação

1. O ID é gerado automaticamente quando a operação entra em `desembolsado`.
2. A regra fica isolada numa função própria, com testes cobrindo os 5 exemplos reais.
3. O ID é gravado na operação e enviado ao HubSpot junto com a mudança de etapa.
4. Se algum dado necessário faltar (data de desembolso, unidade, CNPJ ou tipo de taxa), o ID
   **não é gerado** e a operação sinaliza a pendência — em vez de produzir um código quebrado.
5. O ID gerado é exibido no card e no modal da operação.
6. Colisão é detectada e sinalizada, não silenciada (ver abaixo).

## Risco: colisão de IDs

A regra atual não garante unicidade. Duas operações **no mesmo dia**, de unidades cujo nome
começa igual nas 3 primeiras letras, e com CNPJ começando com os mesmos 2 dígitos, geram
**exatamente o mesmo ID**.

Improvável, mas o volume de operações cresce e o efeito seria silencioso — dois registros
diferentes com o mesmo identificador. Na planilha ninguém perceberia; no sistema dá para
detectar.

**Proposta:** ao gerar, verificar se o ID já existe. Se existir, gravar assim mesmo (para não
travar a operação) mas registrar um alerta visível para a Lavínia decidir.

O formato de 20 caracteres reduz bastante esse risco, por incluir mais dígitos do CNPJ e o
número de parcelas — mais um ponto a favor dele.
