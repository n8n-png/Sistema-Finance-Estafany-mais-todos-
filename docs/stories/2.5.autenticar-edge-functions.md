# Story 2.5 — Autenticar as edge functions e remover o gateway do Lovable

- **Épico:** E2 · **Sprint:** 3 (antecipada) · **Bloqueio:** 🟢 · **Status:** Concluída

## Contexto

Edge functions ficam expostas na internet. Duas delas não verificavam nada.

### `send-operacao-email` — era um relay de e-mail aberto

Sem autenticação, e com `to`, `subject` e `html` livres no corpo da requisição: qualquer
pessoa com a URL podia disparar mensagem arbitrária, para qualquer destinatário, saindo de um
remetente da MaisTODOS. É material de phishing pronto, com a reputação do domínio junto.

Além disso, o envio passava pelo gateway do Lovable (`connector-gateway.lovable.dev/resend`),
que deixa de existir para nós após a migração.

### `forward-to-n8n` — webhook aberto

Repassava qualquer payload para o webhook do n8n da empresa, sem validar JWT, com a URL fixa
no código.

## Critérios de aceitação

1. Ambas exigem JWT de usuário válido.
2. Helper de autenticação compartilhado, para que a próxima function não repita — nem esqueça —
   a verificação.
3. `send-operacao-email` fala direto com o Resend; remetente vem de `EMAIL_REMETENTE`.
4. `N8N_WEBHOOK_URL` sai do código para o ambiente — migrar o n8n cloud para o Dokploy não vai
   exigir alterar código.
5. Limites de tamanho de payload e de número de destinatários.
6. Erros de terceiros não vazam para o cliente; ficam no log.
7. Sem chave configurada, o e-mail responde em **modo simulado** — o fluxo roda inteiro antes
   de o domínio estar verificado.

## Variáveis de ambiente novas

| Variável | Function | Obrigatória |
|---|---|---|
| `N8N_WEBHOOK_URL` | `forward-to-n8n` | Sim |
| `N8N_WEBHOOK_SECRET` | `forward-to-n8n` | Não — o n8n valida `X-Webhook-Secret` |
| `RESEND_API_KEY` | `send-operacao-email` | Não — sem ela, modo simulado |
| `EMAIL_REMETENTE` | `send-operacao-email` | Não — sem ela, modo simulado |
