# Story 3.9 — Vários documentos por item de checklist

- **Épico:** E3 · **Bloqueio:** 🟢 · **Status:** Implementada
- **Origem:** pedido da Lavínia Resende em 06/09/2026

## História

**Como** Lavínia,
**quero** anexar mais de um documento no mesmo item do checklist,
**para que** uma operação com três representantes legais tenha as três identificações
registradas — e dê para saber de quem é cada uma.

## O caso que motivou

> *"seria interessante se tivéssemos a opção de adicionar mais documentos no 'Documento de
> identificação dos representantes legais / avalistas — e caso aplicável, dos cônjuges +
> certidão de casamento'... Pensei agora porque estou fazendo uma operação com 3 RL com
> 3 Outorgas"*

O modelo permitia **um** arquivo por item. Vários itens do checklist são inerentemente
plurais: identificação de cada representante, outorga de cada cônjuge, certidão de cada
casamento.

Sem isso, cada envio sobrescreveria o anterior, e o operador teria que juntar tudo num PDF
fora do sistema — perdendo justamente a informação de qual documento é de quem.

## A sugestão do arquivo zipado

A Lavínia ofereceu uma alternativa: *"clicar e ele abrir uma tela pra anexar todos e virar
um arquivo zipado dentro de uma aba"*.

Adotamos a lista, não o zip, por três razões:

1. **Zip guardado é caixa preta.** Ninguém vê o conteúdo sem baixar e descompactar, e não
   dá para conferir documento por documento — que é exatamente o que o fundo faz.
2. **Substituir um documento exigiria refazer o pacote inteiro.** Uma outorga corrigida
   obrigaria a rezipar tudo.
3. **O fundo abre documentos específicos**, não o conjunto.

O zip continua fazendo sentido — mas na **saída**, ao baixar tudo de uma vez. Isso é
interface, não armazenamento. O botão "Baixar tudo (.zip)" já existe na tela e ganha
utilidade real agora que há vários arquivos por item.

## O que foi implementado

| Camada | Entrega |
|---|---|
| Banco | Tabela `operacoes_formalizacao_anexos`, N por item, com descrição própria |
| Banco | Colunas `anexo_*` removidas do item de checklist |
| Banco | Trigger que sincroniza `checked` com a existência de anexos |
| Banco | RLS herdando a permissão por etapa da operação |
| Serviço | `listarAnexos`, `anexarDocumento`, `renomearAnexo`, `removerAnexo` |
| Interface | Lista de documentos por item, com envio múltiplo e remoção individual |

## Decisões

**Cada anexo tem descrição própria.** É o que responde "de quem é este documento". Sem ela,
três arquivos no mesmo item viram um enigma para quem confere — e quem confere é o fundo.

**`checked` é mantido por trigger, não pela aplicação.** Item com documento está atendido;
item que ficou sem nenhum volta a pendente. Deixar isso na interface abriria espaço para o
checklist dizer que está completo quando não está — e é ele que o fundo usa para decidir se
a documentação está em ordem.

**Envio múltiplo é sequencial, não paralelo.** Em conexão ruim, uploads simultâneos competem
entre si e o progresso fica impossível de acompanhar. Selecionar 3 arquivos de uma vez
funciona; eles sobem em fila.

**O nome do arquivo no Storage recebe prefixo aleatório.** Três outorgas saídas do mesmo
scanner costumam se chamar todas `documento.pdf` — sem o prefixo, uma sobrescreveria a outra.

**Remoção apaga o registro antes do arquivo.** Se a remoção do arquivo falhar, sobra um
órfão no Storage: desperdício de espaço, inofensivo. Na ordem inversa, uma falha deixaria o
checklist apontando para arquivo inexistente — e aí a operação **parece** documentada
quando não está.

**A descrição é editável depois; o arquivo, não.** Corrigir "Outorga da Maria" para "Outorga
da Maria Silva" é rotina. Trocar o arquivo por baixo do mesmo registro apagaria o rastro —
para isso, remove-se e envia-se de novo, e o histórico mostra.

## Nota sobre o modelo anterior

As colunas `anexo_*` foram criadas na Story 3.4, dois dias antes, e removidas aqui sem
migração de dados — o banco ainda não subiu, nenhum arquivo foi enviado. Corrigir agora é
muito mais barato do que conviver com dois lugares guardando anexo.

É também um bom argumento a favor da esteira de evolução: o pedido chegou antes de a
limitação virar dado em produção.

## Descrição no envio — decidido em 06/09

A área confirmou: cada documento recebe um nome. A regra implementada pede a descrição
**apenas quando o item vai ficar com mais de um arquivo**.

Por que não pedir sempre: itens como Cartão CNPJ ou Carta Bacen têm um documento e nome
óbvio — exigir descrição ali seria atrito sem ganho. A descrição existe para distinguir, e só
há o que distinguir quando há mais de um.

O campo já vem preenchido com o nome do arquivo sem extensão: costuma ser um ponto de partida
melhor do que campo vazio.
